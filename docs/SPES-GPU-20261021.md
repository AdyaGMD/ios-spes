# Adreno 610 reuse audit — 2026-10-21

GPU acceleration is not enabled on spes. The current iOS UI and volume keys
work according to the user, but respond very slowly. This audit separates
source availability from hardware validation.

## Reusable source

[UniXNU's Adreno documentation](https://unixnu.com/drivers/native-adreno)
points to public source, unlike the unpublished accelerator implementation in
ios-topaz. Downloaded snapshots are in ignored `research/unixnu`:

- NativeAdreno `805c7e4bfb7451eb6923f4a14dea8c657b9be7d2` (MIT).
- NativeMetal `6dcd4cbb69eb5625988706de42aa8ad3009b8ee7`.
- ArmSmmu4K `4d0d6598b1a36aeec3de01091893fa6660e49388`.
- AdrenoFirmware `40fdb8ea87606612ac6f1e80bbb49955d0ce4051`.
- AdrenoPM4 `445f8fe6d115738352b9d78dc70af6d61aa7f62f`.

Candidate reuse: native Metal frontend, Darwin Turnip transport ABI, buffer
management, fences, and SMMUv2 table algorithms. Preserve each component's
license on import. No driver source has been added to the kernel yet.

## Why the A740 driver cannot simply be enabled

NativeAdrenoService directly uses Sheng GMU startup and `buildA740`, with
A740 SQE/preemption state. Its GPU state machine requires `bootGmu` before
SMMU and ring startup. NativeMetal/Turnip integration is useful above this
hardware-specific layer; it does not supply an A610 kernel backend.

The phone's Android source at
[Jabiyeff/kernel_xiaomi_sm6225, 6c2b3e7](https://github.com/Jabiyeff/kernel_xiaomi_sm6225/blob/6c2b3e7528a0778cd80c95eabb490746b5422f8c/drivers/gpu/msm/adreno-gpulist.h)
identifies A610 with `a630_sqe.fw`, `a610_zap`, 132 KiB GMEM, and no
ADRENO_GPMU feature. `adreno_a6xx.c` explicitly skips GX power-domain register
access for A610. This refers to internal register handling: the live spes FDT
still describes external CX/GX GDSCs. Do not copy A740 GMU/GX sequences or firmware.
The Linux source is a reference, not incorporated into this project.

UniXNU uses 4 KiB GPU translation tables; our XNU uses 16 KiB CPU pages.
Different CPU/GPU page sizes are not by themselves disqualifying, but physical
subpage ownership, allocation alignment, cache maintenance, user mappings and
teardown must be audited. Do not assume this requires changing CPU page size.

## Hardware inventory from live FDT

`python3 tools/spes-gpu-profile.py dtb/spes-live.dtb` reports only GPU-related
properties and refuses a different chip ID. It performs no hardware accesses.

| Resource | Address | Length |
| --- | --- | --- |
| Chip ID | `0x06010001` | A610 revision 1 |
| GPU | `0x05900000` | `0x90000` |
| CX debug | `0x05961000` | `0x800` |
| GPU SMMU | `0x059a0000` | `0x10000` |
| TCU | `0x059c2000` | `0x20` |

These are resource descriptions, not evidence that registers are powered or
safe to access. Stream/context ownership still needs validation.

## Validation and next stages

- Live FDT inventory passed; a modified wrong-chip FDT was rejected.
- Unmodified ArmSmmu4K table host tests passed with Clang ASan/UBSan:
  independent table walks, boundaries, address widths and transactional refusals.
  This validates host algorithms only, not the phone's SMMU configuration.
- Recovery identifies `Adreno610v2`, with current GPU clock 320 MHz and
  advertised frequencies 320/465/600/785/1025/1114.8 MHz. These are Linux
  observations; XNU GPU clock state is unknown.
- Recovery logs explicitly report non-coherent SMMU table walks and four stream
  match groups. Cache maintenance must be explicit; do not inherit coherent
  assumptions from another platform.
- Copied six A610 ZAP/A630 SQE files from vendor mounted `ro,noload`, verified
  each host hash against recovery, then unmounted it. Local files and manifest
  are in ignored `research/spes-gpu-firmware`. No firmware was loaded into XNU.
  SQE is 32264 bytes, SHA256
  `57eece0d8032b0ab2467d856c304ce22f502ae8d4b2f8169b9d1ca890ceb463c`.
- Next: implement an opt-in A610 power/SMMU backend using the verified firmware,
  beginning with clock/regulator, TrustZone ZAP and context ownership checks.
- Require an isolated command/fence test before a GPU fill/copy test. Require
  verified GPU output and cache visibility before exposing a Metal device.
- Preserve the working 0096 image; do not advertise an accelerator service as
  working before its backend passes those tests.

## Stage 0: bootloader clock/power inventory

Patch 0097 adds an opt-in `spesgpuprobe=1` snapshot of GPUCC and GCC control
registers. `tools/build-spes-diagnostic.sh KERNEL LIVE_FDT gpu` runs it through
the delayed touch worker using a RAM root and visible console. It performs no
GPU core or SMMU access and no GPU register writes. It does not initialize the
GPU. Full iOS image defaults are unchanged.

Recovery lacks debugfs and /dev/mem. Both external GDSCs report disabled with
zero users, so Linux's 320 MHz sysfs value alone does not prove active clocks.
The FDT identifies CX/GX control at 0x0599106c/0x0599100c, parent supply
pm6125_s3_level, and ZAP PAS ID 13. The GPUCC also depends on the MX supply.
Firmware allocation and PAS ownership must be resolved before ZAP startup.

## Command/firmware preparation findings

The pinned Android `_load_firmware` uploads SQE bytes starting at file offset 4;
for this phone the device code is 32260 bytes (8065 words), not the whole
32264-byte file. Its A610 `CP_ME_INIT` packet has 11 payload words via
`_set_ordinals`, unlike UniXNU's A740 seven-word payload. Preserve the A610
header-dump/workaround slots and register-list semantics when implementing
submission; do not reuse the A740 initializer unchanged.

The copied ZAP MDT is ELF32 with three program headers. Its only PT_LOAD
segment has relocation flag bit27, nominal address 0x5000, file/memory size
0x830 and alignment 0x100000. That nominal address is not a safe physical load
address. A real contiguous allocation and the Qualcomm relocation/authentication
protocol are required. No physical ZAP destination has been selected yet.
